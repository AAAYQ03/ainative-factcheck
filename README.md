# 投顾稿件核查台（AI Native 投资内容质量治理）

投顾或内容运营把**待发布的盘后点评、个股解读**粘贴进来，系统会做两件事：

1. 自动核对稿件里的行情、估值、财务数字，逐条与扶摇数据源比对；
2. 检查收益承诺、确定性预测、直接买卖建议等合规风险。

每条结论都附**数据源接口、字段、原值、时点、单位和计算口径**。用户逐条"采纳/驳回"后生成修订稿，并可导出可审计的核查报告。

- **线上地址：https://factcheck.clubmatch.win** （Cloudflare Workers + 自定义域名，国内可直接访问；备用地址 https://ainative-factcheck.q16637106928.workers.dev）
- 源代码：https://github.com/AAAYQ03/ainative-factcheck
- 赛题：题目 14，开放命题 · AI Native 投资产品创新（投资内容生产 / 质量治理）

## 1. 问题定义

| | |
|---|---|
| **目标用户** | 券商财富管理部的投顾、投顾内容运营；次要用户为合规审核岗 |
| **真实工作流** | 投顾每天盘后写点评，发给客户群或 App 之前，需要自己或合规岗把稿件里的每个数字与行情软件逐一核对，再人工排查"稳赚""目标价""建议买入"这类违规表述 |
| **痛点** | 单篇稿件人工核对约 15–30 分钟；数字写错（涨跌方向写反、增速记错年份）和违规表述是投顾展业中常见的合规问题，漏掉一处就可能招致投诉或监管处罚 |
| **非目标** | 不生成投资观点，不预测涨跌，不给买卖建议，不替代合规负责人签字，不评价观点本身对错 |
| **成功标准** | ① 单篇核查耗时从约 20 分钟降到 2 分钟以内（实测一次核查 10–30 秒，加上人工逐条处理）；② 支持类型的数值陈述自动覆盖率 ≥ 90%；③ 构造的违规样例召回率 100%，合规稿件规则层零误报；④ 每条"一致/不符"结论 100% 带可追溯的来源字段；⑤ 数据缺失或接口失败时 0 次输出"通过" |

## 2. 为什么需要 LLM，而不只是规则、搜索或传统数据产品

| 方案 | 能做到 | 做不到 |
|---|---|---|
| 关键词规则 | 拦截"稳赚""必涨"等显式违规词 | 看不懂"可以考虑上车""跌出价值、主力即将拉升"这类委婉或变相表述；也无法从自由文本里抽出"宁德时代 / 10月21日 / 日涨跌幅 / −8.5%"这样的结构化陈述 |
| 搜索 / 行情软件 | 人工逐个查数 | 每个数字都要人去找对应的口径、日期和复权方式，耗时且容易查错 |
| 传统数据产品 | 提供准确数据 | 不理解稿件，不知道稿件里哪句话需要查、该查哪个字段 |
| **本产品** | **LLM 负责理解**：拆解陈述、识别指标、日期、口径、比较方向，并做语义合规判断；**确定性代码负责计算**：调用扶摇接口、计算涨跌幅和同比、按容差比对 | 不让 LLM 生成任何数字。LLM 输出的每条引用都必须是原文子串，否则丢弃 |

## 3. 系统闭环

```
稿件 ──┬─► [LLM] 抽取数值陈述（指标/标的/日期/窗口/财年/比较方向）──► 原文子串校验（丢弃编造的引用）
       │                                   │
       │                                   ▼
       │          [工具] 扶摇 API：标的检索 → 行情快照 / 日K / 估值快照 / 年报利润表
       │                                   │
       │                                   ▼
       │          [规则] 计算 + 容差比对 + 时效检查 ──► ✅一致 / ❌不符(附建议值) / ⚠️无法核实(附原因)
       │
       └─► [规则引擎] 合规关键词（LLM 不可用时依然生效）
           [LLM] 语义合规审查（变相建议、夸大、观点未标注）──► 原文子串校验
                                   │
                                   ▼
          综合结论：需修改 / 需人工复核 / 核查未完成 / 核查项一致（仍待合规签字）
                                   │
                                   ▼
   [人] 逐条 采纳 / 驳回 ──► 修订稿（只应用采纳项）+ Markdown 核查报告 + 反馈统计（采纳率，用来评估误报）
```

- **数据**：扶摇 REST API，用到 `/api/meta/tickers/search`、`/api/a-share/prices/snapshot`、`/api/a-share/prices/historical`、`/api/a-share-index/prices/snapshot|historical`、`/api/a-share/valuations/snapshot`、`/api/a-share/financials/income-statements`
- **工具调用**：同一请求内按 key 缓存，同一标的不重复请求。每次调用都记入 Agent 执行轨迹（参数、耗时、request_id、错误码），页面上可以展开查看
- **状态**：核查结果、逐条决策和修订稿在页面状态中维护；反馈统计存于浏览器 localStorage
- **人机协作**：AI 只给标注和建议，所有修改都要人确认；"无法核实"项只能标记为"已人工核对"，不能"采纳"
- **风险控制**：见第 6 节

## 4. 本地启动

```bash
npm install --legacy-peer-deps
cp .env.example .env.local   # 填入 FUYAO_API_KEY、DEEPSEEK_API_KEY
npm run dev                  # http://localhost:3000（本机解析不了扶摇域名时用 npm run dev:localdns）
npm test                     # 离线测试（mock 数据，不消耗额度）
npm run smoke -- wrong-numbers   # 用真实接口跑示例稿件：clean | wrong-numbers | compliance
```

| 环境变量 | 必需 | 说明 |
|---|---|---|
| `FUYAO_API_KEY` | 是 | 扶摇金融数据 API Key，只在服务端使用 |
| `DEEPSEEK_API_KEY` | 是 | 运行时 LLM |
| `DEEPSEEK_MODEL` | 否 | 默认 `deepseek-flash` |
| `FUYAO_BASE_URL` / `DEEPSEEK_BASE_URL` | 否 | 覆盖接口地址 |

技术栈：Next.js 15.5（App Router，Route Handler 作后端）+ TypeScript + Tailwind + Vitest；部署在 Cloudflare Workers（`@opennextjs/cloudflare`）。

部署：`npx wrangler secret put FUYAO_API_KEY`、`npx wrangler secret put DEEPSEEK_API_KEY`，然后执行 `npm run cf:deploy`。构建前不要放 `.env.local`，否则 OpenNext 会把其中的变量打包进 Worker。

## 5. 核查口径

| 指标 | 数据来源 | 口径 | 容差（精确 / 模糊表述） |
|---|---|---|---|
| 当日涨跌幅（未写日期） | 行情快照 `price_change_ratio_pct` | 最新价 / 前收 − 1；盘中取数不是收盘值 | ±0.1pp / ±1pp |
| 当日涨跌幅（写了日期） | 日K（前复权）`close_price` | 当日收盘 / 前一交易日收盘 − 1 | 同上 |
| 收盘价 | 快照 `last_price`，或日K（不复权） | 原始价格 | ±0.5% / ±2% |
| 区间涨跌幅 | 日K（前复权） | 末日收盘 / 窗口起点或之前最近交易日收盘 − 1；窗口按自然日计 | ±0.1pp / ±1pp |
| PE TTM / MRQ、PB、PS | 估值快照 | 原值不四舍五入 | ±3% / ±8%（估值随股价每日变化） |
| 营收、净利润、归母净利润 | 年报利润表（整体合并） | 原币元 ÷ 1e8 = 亿元 | ±1% / ±3% |
| 营收、归母净利润同比 | 年报利润表 | 本年 / 上年 − 1 | ±0.1pp / ±1pp |

"超过 / 逾 / 至少"按下限判断，"低于 / 不足"按上限判断；涨跌方向相反时不论数值差多少都判为不符。

## 6. 失败条件与合规边界

**不会输出"一致"的情况**（一律标 ⚠️ 无法核实，并写明原因）：
- 接口超时（10 秒）、网络错误（重试 1 次后仍失败）、HTTP 429 或业务码 4001 限流、Key 无效（2001/2003）、标的不存在（3001）
- 快照或K线时点距今超过 4 天，视为过期
- 指定日期没有K线（非交易日或停牌），或缺少前一交易日数据
- 年报尚未披露、缺上年数据无法算同比、估值字段为 null（亏损或净资产为负时）
- 指标不在支持范围内（例如"跑赢大盘""市占率"）
- LLM 不可用或返回非法 JSON：整体结论为"核查未完成"，只保留规则合规扫描的结果

**合规边界**：
- 产品自身不输出任何涨跌预测、收益承诺或买卖建议；所有改写建议都不得新增数据（写在 prompt 约束里）
- 页面和报告都写明"不构成投资建议""发布前仍需合规负责人签字"；即使全部一致，结论也只是"待签字"，不是"可发布"
- 区分事实、推断和观点：LLM 对每句话标注性质；推断没有使用限定词时提示"观点未标注"，这类只作建议，不阻断发布
- API Key 只在服务端使用，不写入仓库（`.env*` 已加入 gitignore）；示例稿件为构造内容，不含用户隐私

**已知边界 / 未做事项**：
- 只覆盖 A 股个股与指数的日频数据和年报；季报、"跑赢指数"类相对收益、资金流、新闻和政策事实暂未核查（后续可接入 iFinD MCP 的新闻、资金、宏观工具来核对"消息面"陈述）
- 时效阈值用固定 4 天，没有接交易日历，长假后首个交易日可能出现误报"过期"
- 合规规则只是示例级词表，没有对接机构内部的合规知识库
- 反馈统计只存在本机浏览器，没有做多用户后端
- 并发压力下扶摇可能限流：线上同时发起 6 个核查时，曾有一次 6 条全部返回"无法核实"。系统如实降级，没有误判成一致，但吞吐量有上限；后续需要加请求队列和退避重试
- LLM 抽取有漏抽的可能：漏抽的数字不会出现在核查列表里，所以页面上会高亮已核查的片段，方便人工发现未覆盖的数字

## 7. 后续验证计划

1. **离线评测集**：从公开投顾内容中脱敏或改写 100 篇，人工标注数值陈述和违规表述，测量抽取召回率、核查准确率、合规召回率和误报率
2. **影子模式试点**：找 3–5 名投顾使用 2 周，对比人工核查耗时和漏检数；以页面上的"驳回率"作为误报信号，迭代 prompt 和词表
3. **上线门槛**：数值核查准确率 ≥ 98%、合规高风险项召回率 ≥ 95% 之后，才考虑把它作为合规岗的前置工具
